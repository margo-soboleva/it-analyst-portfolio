# Кейс: сервис представления остатков

## Контекст и задача

Клиентским приложениям требовался доступ к данным об остатках товаров. Источник данных — учётная система; для передачи данных используется интеграционная платформа. Отдельный сервис предоставляет данные клиентам через API.

Цель решения — отделить получение данных из исходной системы от клиентских запросов и предоставить согласованный интерфейс для чтения остатков.

## Моя роль

- Собирала и уточняла требования у заказчиков.
- Определяла источники данных и участвовала в проработке взаимодействия систем.
- Совместно с архитектором обсуждала архитектуру и взаимодействия; подготовила диаграммы.
- Самостоятельно проектировала API.
- При необходимости создавала необходимые объекты в интеграционной платформе.
- Формулировала задачу ABAP-разработчику на передачу данных из учётной системы в интеграционную платформу.
- Описывала задачу backend-разработчику на интеграцию данных из интеграционной платформы в сервис.
- Описывала бизнес-логику полей API, обработку ошибок и альтернативные сценарии.

## Принятые допущения и границы схемы

Схемы показывают логический поток данных: учётная система → интеграционная платформа → сервис → клиентские приложения. Известно, что данные поступают в базу данных сервиса через интеграционный процесс. Детали реализации этого процесса, состав компонентов и конкретный протокол каждого внутреннего взаимодействия здесь не фиксируются, если они не нужны для понимания кейса.

Названия систем и сервисов обезличены. Kafka упоминается только в тех местах, где речь идёт об использовании Kafka в интеграционном потоке.
