# Сервис представления остатков

## Зачем понадобился отдельный сервис

Остатки — это информация, на которую клиентские приложения опираются, когда показывают покупателю доступность товара. Её нужно получать быстро и в удобном для клиентских сценариев виде.

При этом исходные данные находятся в учётной системе, которая не рассчитана на то, чтобы быть источником для большого количества частых запросов от пользовательских приложений. Если каждое приложение будет напрямую зависеть от неё, растёт связность между системами, а сама учётная система становится частью клиентского пути.

Поэтому данные об остатках выносятся в отдельный сервис. Он получает их через интеграционный процесс, хранит у себя и предоставляет клиентским приложениям через API.

## Какую задачу решает проект

Проект создаёт отдельный слой между учётной системой и приложениями, которым нужны остатки. Клиентам не нужно знать, где и как исходно формируются данные: они обращаются к понятному API сервиса.

Для бизнеса это важно потому, что информация о доступности товара используется в клиентских сценариях выбора товара и покупки. Для продуктовой команды отдельный сервис позволяет развивать способ предоставления остатков, не привязывая каждый клиентский сценарий напрямую к устройству исходной учётной системы.

Это ожидаемая ценность архитектурного решения, а не заявление о подтверждённом проценте ускорения или экономии: конкретные бизнес-метрики в этом публичном кейсе не приводятся.

## Как устроено решение

Данные передаются из учётной системы через интеграционную платформу и интеграционный поток, затем сохраняются в базе данных сервиса. Клиентские приложения запрашивают остатки через API сервиса.

Так разделены две задачи: доставка и обновление данных — с одной стороны, выдача данных клиентам — с другой. Это также позволяет проектировать API с учётом потребностей потребителей, а не повторять структуру исходной системы.

## Мой вклад

- Собирала и уточняла требования у заказчиков и выясняла, какие данные нужны клиентским сценариям.
- Определяла источники данных и участвовала в проработке взаимодействия систем.
- Совместно с архитектором обсуждала архитектуру и взаимодействия; подготовила диаграммы.
- Самостоятельно проектировала API: описывала поля, бизнес-логику, ошибки и альтернативные сценарии.
- При необходимости создавала необходимые объекты в интеграционной платформе.
- Формулировала задачу ABAP-разработчику на передачу данных из учётной системы в интеграционную платформу.
- Описывала задачу backend-разработчику на интеграцию данных из интеграционной платформы в сервис.

## Границы публичного описания

Названия систем, сервисов и клиентов обезличены. Схемы показывают логический поток данных: учётная система → интеграционная платформа → сервис → клиентские приложения. Подтверждено, что данные поступают в базу данных сервиса через интеграционный процесс; детали реализации этого процесса не раскрываются там, где они не нужны для понимания решения.

В кейсе не публикуются внутренние идентификаторы, реальные контракты и количественные показатели, которые нельзя подтвердить или раскрыть публично.
