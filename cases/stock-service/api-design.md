# Подход к проектированию API

Этот документ описывает аналитический подход к проектированию API сервиса представления остатков. Конкретные endpoint, поля и коды ответов не приводятся, чтобы не выдавать обезличенный пример за полную спецификацию промышленного API.

## Что необходимо определить

1. **Назначение и потребители** — какие клиентские сценарии должен поддерживать API.
2. **Ресурс и контракт** — идентификаторы, обязательные и необязательные параметры, структура ответа.
3. **Бизнес-правила** — как трактуются остатки, единицы измерения, источники и граничные значения.
4. **Валидация** — какие параметры проверяются и при каких условиях запрос отклоняется.
5. **Ошибки** — формат ошибки, причины отказа и поведение для некорректных или отсутствующих данных.
6. **Альтернативные сценарии** — частичные данные, отсутствие записи, некорректные параметры и недоступность зависимостей, если такие сценарии предусмотрены требованиями.
7. **Интеграции** — происхождение данных и ответственность каждого компонента.
8. **Проверяемость** — критерии приёмки, примеры запросов и ответов, позитивные и негативные проверки.

## Артефакты аналитика

В зависимости от задачи контракт можно описать в OpenAPI/Swagger или TypeSpec, а поведение дополнить:
- таблицей полей и правил заполнения;
- примерами запросов и ответов;
- таблицей ошибок и условий их возникновения;
- Acceptance Criteria;
- диаграммой последовательности для интеграционного сценария.

## Важное ограничение

Это описание подхода, а не готовая спецификация API. Перед публикацией конкретного контракта необходимо отдельно проверить, какие детали разрешено раскрывать публично, и удалить любые внутренние идентификаторы, данные клиентов и конфиденциальные правила.
